# SkillHive 公开市场连接器与需求探索产品方案

版本：v2.0（公开市场发布与员工令牌授权基线）
编制日期：2026-09-05
适用范围：SkillHive 公开市场第三方连接器（MCP + Skill）、SkillHive 企业需求探索与结果归集
文档性质：产品设计与研发验收依据；不是已实现功能清单，不代表平台审核通过。

本次修订：连接器按个人实名认证开发者主体提交 WorkBuddy 公开市场，市场对所有用户可见和可安装；安装不代表企业授权，服务端继续仅接受目标企业管理员签发的有效员工令牌。平台发布主体、市场可见范围、企业数据授权和目标企业推广状态分别记录，不以平台审核通过替代企业侧上线验收。需求探索继续作为内置应用，应用配置拥有应用 Skill 的关联和激活关系。

## 1. 产品决策摘要

公司启用一个内置“需求探索”应用。员工在 WorkBuddy 中通过 SkillHive 公开市场连接器使用该应用，与 AI 逐步澄清业务问题；阶段性成果和最终需求通过 MCP 工具回传公司服务器，形成可追踪、可评审的企业需求池。

本期选择“公开市场第三方连接器 + 企业 Skill 助手 + 应用快捷入口 + 服务端版本化业务规则 + 结果回传工具”。企业 Skill 助手统一发现员工可见的普通 Skill 和应用，并按入口类型路由；需求探索快捷入口保留为兼容的显式入口。SkillHive Web 仅承担管理员运营，服务端负责规则、员工身份、权限、持久化和需求管理；WorkBuddy 是员工唯一业务交互入口。

核心决策：

- 采用 MCP + Skill，不采用 CLI + Skill，不以 WorkBuddy OpenAPI 云端任务作为本期执行入口。
- 连接器由个人实名认证开发者主体提交，服务类目选择“商业服务—企业管理”；平台审核通过只表示允许进入市场，不表示该连接器由 WorkBuddy 官方运营或背书。
- 市场可见范围为公开，所有 WorkBuddy 用户都可以查看和安装；安装、启动或看到令牌输入框均不构成企业数据授权。
- 企业数据访问资格只由 SkillHive 服务端验证的员工令牌决定。未提供令牌、令牌无效、令牌不属于目标企业或权限范围不足时，不返回企业 Skill、应用、需求或员工数据。
- Web 仅允许管理员登录；不提供员工注册、密码登录、个人中心、本人结果网页或自助令牌页面。员工档案是业务身份，不是 Web 登录账号。
- 首期由管理员为每位员工发放独立 MCP 接入令牌，通过受控渠道定向交付；不使用全员共享令牌，旧用户 PAT 不再作为 MCP 接入凭证。
- 连接器内仅包含企业 Skill 助手、应用快捷入口和稳定工具契约；公司普通 Skill、业务规则与资源保留在企业 SkillHive，不打包公开。
- “需求探索”归类为内置应用：应用负责固定流程、状态、数据、权限和 MCP 工具；与应用绑定的 Skill 仅负责可编辑、可版本化的提示词、方法和模板。
- 普通 Skill 和应用 Skill 使用同一上传发布流程；只有管理员可以发布应用 Skill。发布时仅确定不可变的用途类型，不关联具体应用；应用配置页负责按固定契约筛选、关联并激活兼容版本。发布不自动激活。
- 同一发布入口通过平台字段 `skill_type` 建立不可变用途分类；发布时不关联具体应用，已有标识不能在普通 Skill 与应用 Skill 之间转换。需求探索在应用配置中关联并激活满足其固定契约的应用 Skill 版本。
- 面向本公司预置企业服务地址。员工从公开市场安装连接器并完成员工令牌认证后，即可按需获取和使用公司发布的技能，无需填写地址、编辑 JSON，或因普通技能更新重复安装与配置。
- 首期身份认证采用一次填写员工专属令牌的方式，不等同于已经实现 OAuth 登录授权；令牌失效、更换设备等情况下可能需要管理员补发并重新连接。不承诺无人操作的全员安装或后台强制刷新。
- 自动回传仅针对当前需求探索的业务成果，不采集员工其他对话，也不承诺完整聊天记录归档。
- 阶段性草稿一旦成功保存到公司服务器，即可由管理员在运营平台查看。
- 最终提交表示“进入公司需求池”，不表示员工已完成正式签署或业务评审通过。
- 员工在 WorkBuddy 内查看回执、继续探索、补充与重新提交，不跳转到 SkillHive 登录或核对内容；正式签署不在本期范围。
- 新建“需求探索”业务模块，不把结果直接写入现有全员可见的“许愿墙”。

本方案中的工具名、页面路由、字段、指标阈值和分期安排均为 SkillHive 拟定设计；不是 WorkBuddy 平台已有功能。

## 2. 背景、目标与范围

### 2.1 业务问题

员工通常能描述不便，却难以直接写出可评审的需求。公司希望通过统一的探索方法，帮助员工把模糊想法整理成具体问题、目标、收益和验收条件，同时避免成果停留在个人对话中。

### 2.2 产品目标

1. 统一方法：全员使用公司发布的需求探索规则，每次探索可追溯所用版本。
2. 降低门槛：员工以自然语言讨论，不必手工撰写完整 PRD 或复制结果到另一个系统。
3. 形成记录：以服务器保存记录和提交回执为准，区分草稿、正式提交和业务评审。
4. 保护边界：员工只能读写本人探索；管理员可查看全部已保存草稿和正式提交，但只能对正式提交执行评审，不能代员工修改内容。
5. 支持改进：按版本观察探索启动、保存、提交、待补充情况，帮助公司改进技能。

### 2.3 本期范围（MVP）

- 预置本公司服务地址的公开市场第三方连接器包、接入指引、兼容性测试与提交审核材料。
- 一个内置“需求探索”应用、一份统一发现普通 Skill 和应用的企业 Skill 助手、一个需求探索兼容快捷入口，以及一套可初始化或从统一入口上传、再由应用选择版本的公司级业务规则。
- 管理员登录、员工档案、独立令牌发放/轮换/吊销。
- 员工首次连接和权限检查。
- 启动、读取、阶段保存、继续探索、最终提交。
- 员工在 WorkBuddy 内查询本人探索与评审反馈；管理员运营平台查看全部已保存草稿、正式需求并完成基础评审。
- 幂等写入、版本冲突处理、失败回执、WorkBuddy 内补交、基础审计。
- 脱敏试点、正式发布检查和回退机制。

### 2.4 本期不做

- OpenAPI 账号绑定、云端执行中心、本地助理消息历史采集。
- 员工 Web 登录、个人工作台、自助领令牌网页、结果分享页和免登录个人详情链接。
- 企业 SSO、组织通讯录同步、全员静默安装、Buddy 应用封装。
- 面向多家企业的自助地址配置、动态企业发现和企业切换。
- 所有聊天逐轮无遗漏归档、离线后台补传、自动审批工具权限。
- 附件上传、本机目录扫描、脚本执行、自动操作其他业务系统。
- 跨员工对话共享、多人实时共同编辑、公开需求投票。
- 自动需求去重合并、AI 优先级决策、项目排期和交付管理。

“汇总”在 MVP 中指集中存储、检索、分类和数量统计；跨员工语义聚类与报告生成属于后续分析能力。

## 4. 平台依据与接入设计

### 4.1 已核实的平台能力

官方支持通过 MCP + Skill 连接器扩展服务；远程 MCP 可使用 HTTPS SSE 或 Streamable HTTP，连接器包经审核进入市场。服务地址可以在 MCP 配置中固定，Token 模式提供凭证表单，OAuth 则是另一种认证方式。连接器可附带指导工具使用的 Skill。以上字段和提交前检查已于 2026-09-04 按公开文档复核；平台后台可用标识、审核结论和真实客户端行为仍以接入时结果为准。[WorkBuddy 连接器规范](https://open.workbuddy.cn/docs/connector)

以下为本项目据此作出的产品选择，仍需实际客户端联调与审核验证。

### 4.2 连接器定义

| 项目 | 本期设计 |
| --- | --- |
| 展示名称 | SkillHive 技能蜂巢 |
| 主要用途 | 使用企业需求探索方法，保存并提交本人需求 |
| 部署范围 | 本公司专用；不要求员工选择企业或配置服务地址 |
| 连接器标识 | 拟使用 `skillhive`；正式值需确认平台可用性 |
| 接入与认证 | `type: mcp`，`auth_mode: token` |
| 协议 | 优先 Streamable HTTP；联调可使用人工批准的 HTTP/IP `/mcp`，正式发布由发布人员确认平台协议要求 |
| 服务地址 | 由 IT 在发布前确定并预置到连接器包；员工接入表单不展示地址输入项 |
| 令牌 | 管理员按员工档案发放的独立“需求探索”接入令牌 |
| 入参表单 | 仅员工专属令牌，采用密码输入；附“向公司管理员领取/补发”的说明，不附个人登录或领令牌链接 |
| 包版本 | 当前源包 `1.3.0`；与公司业务规则版本独立 |
| 客户端基线 | 拟声明最低 `4.24.0`，覆盖所用 Token 表单及中英文示例字段；发布前按最新规范和实际安装包复核 |
| 分发 | 官方市场为正式入口；现有手动配置保留为兼容与应急入口 |

仓库已交付 `integrations/workbuddy/skillhive` 连接器源目录，包括 `connector-meta.json`、`mcp.template.json`、`token-schema.json`、`icon.svg`、`skills/enterprise-skill-assistant/SKILL.md` 和 `skills/requirement-exploration/SKILL.md`。真实企业地址不进入 Git；`pnpm connector:build -- https://企业域名/mcp` 在忽略目录中生成带 `mcp.json` 的待审核包。仓库不会代替企业上传或提交平台审核。

`mcp.json` 的 `url` 写入经 IT 人工确认的公司 HTTP(S) MCP 完整地址，可为域名或 IP，不再通过 `${MCP_URL}` 接收员工输入。`${SKILLHIVE_PAT}` 作为兼容性的变量名保留，值改为管理员发放的员工专属令牌，通过 Authorization 请求头传递。`token-schema.json` 只定义令牌输入项；固定的是地址，不是所有员工共用的令牌。

不得把凭据放进 URL、入口 Skill、示例、日志或公开安装包；不得分发服务间内部令牌。员工应从 WorkBuddy 公开市场中经公司确认的 SkillHive 连接器入口接入，不把专属令牌填入来源不明的连接器。公开包中的固定企业服务地址不属于访问凭据。

IT 负责协议、域名或 IP、TLS、监听范围、网络可达性及发布包地址的人工校验；代码不再自动拒绝 HTTP、IP、本机地址或测试域名。稳定域名仍可通过 DNS 或反向代理维持后端迁移，避免员工重新配置；若对外地址或路径改变，应按连接器更新流程发布并验证旧版本过渡，不让员工自行改地址。开发/测试包使用独立测试地址和测试令牌，不将生产令牌发往测试服务。

真实企业地址尚待 IT 确认，本文件不虚构域名。固定服务地址可能随连接器元数据对外可见，发布前需确认该地址可以披露；企业内部 Registry 地址仍仅由服务端配置，不写入公开包，也不根据模型参数动态改写。

当前手动配置默认使用 `/sse`。新增连接器使用 `/mcp` 时不直接把现有 `PUBLIC_MCP_URL` 改为 `/mcp`；需分别验证两种入口、代理和配置生成逻辑，保留原客户端兼容性。

### 4.3 应用、入口 Skill 与业务规则

需求探索首先是一个内置应用，不是可由普通 Skill 自行声明的通用能力。三层职责如下：

| 层级 | 职责 | 是否可由管理员编辑 |
| --- | --- | --- |
| 需求探索应用 | 固定业务流程、状态机、数据模型、权限、归集、审计和 MCP 工具 | 不在 Skill 编辑器中修改，随产品版本升级 |
| 企业 Skill 助手 | 从普通 Skill 与独立应用目录统一发现能力；不检索应用内部 Skill | 随连接器包升级 |
| 需求探索快捷入口 | 为既有用户和显式菜单选择提供直接入口，最终进入同一应用流程 | 随连接器包升级 |
| 应用内置业务 Skill | 提问方法、规则正文、模板、参考资料和输出要求 | 可以；每次发布形成新的不可变版本 |

企业 Skill 助手是公开、稳定的统一入口：先按员工身份和部门可见范围过滤，再对普通 Skill 与应用统一加权检索。名称和管理员配置的触发词优先于最新发布版本标签，简介和分类仅作兜底；普通 Skill 在详情页配置触发词，应用在自身配置页配置触发词，应用 Skill 不单独配置。普通 Skill 通过 `get_skill` 加载当前发布版本；应用根据 `entryTool` 进入固定流程，应用内部 Skill 不参与搜索且不能从通用 Skill 接口读取。检索结果显式返回 `entryType` 和 `applicationKey`。需求探索快捷入口继续提供直接进入需求探索的明确路径。两个入口都不包含公司业务资料、固定员工身份或真实凭据。

应用 Skill 是公司私有规则：探索阶段、问题策略、输出格式、可用参考资料和行为限制。发布入口仅将其标记为 `application`，不写入应用归属；Skill 标识可以独立命名。仓库在 `examples/seed-skills/requirement-exploration/` 提供 1.2.0 Grill Me 基线正文、讨论方法、机器可读访谈协议和内容 Schema。兼容版本必须包含并引用 `discussion-playbook.md`、`exploration-content.schema.json` 和 `grilling-protocol.json`，后者必须声明完整 frontier、决策树、角色边界与确认约束。访谈协议独立于 Skill 包版本：旧协议 1.0 保持文本问答兼容，新基线采用协议 1.1，增加 WorkBuddy 原生问答弹窗优先、互斥选项单选、可并行选项多选和编号文本降级规则。旧协议版本仍可选择和回退；暂停当前绑定不重新校验访谈内容，启用或换绑仍需通过兼容性校验。管理员可以初始化该基线，也可以从统一发布页上传应用 Skill；随后在应用页面从满足需求探索契约的候选版本中选择。该目录不进入公开连接器包。

官方 Skill 元数据与当前内部解析器并非完全一致，例如多语言描述、作者以及 `allowed-tools` 与 `allowed_tools` 的表示差异。实施时增加独立的连接器包校验/导出适配，不直接假设内部技能 ZIP 可原样上架。[WorkBuddy Skill 格式](https://open.workbuddy.cn/docs/skill)

- 新探索：服务端在一个一致性操作中读取当前激活版本、建立探索记录并返回同版规则和资源清单。
- 已有探索：继续使用启动时锁定的版本，不因后台发布新规则而中途换版。
- 规则更新：管理员从统一发布页上传应用 Skill 新版本，再到应用页面独立选择并激活。只有激活后的版本用于新探索。
- 常规回退：管理员将激活指针切回此前版本，新探索使用回退版本；不覆盖历史内容。
- 紧急停用：管理员可停用入口或禁止某版本继续探索；已有记录可查看，写入被拒绝并说明原因。
- 连接器更新：改变入口工具协议或兼容性时发布新包；普通公司规则更新不要求每次重发包。

客户端可能缓存菜单和入口 Skill；“自动获取”以启动工具实际返回的规则版本为准，不以菜单显示已刷新为验收依据。旧入口与新服务端不兼容时明确提示升级，不静默降级为无回传的普通聊天。

需求探索的所有受支持入口都必须经过 `start_exploration` 或 `get_exploration`。现有动态 prompt 和 `get_skill` 可能取得普通技能的最新发布版本，并不天然理解探索的激活指针；针对需求探索入口需补充引导和兼容处理，不能把“最新发布”误当成“已激活”。其他普通技能的读取行为保持不变。

## 5. 角色、身份和权限

### 5.1 两类身份与权限矩阵

管理员账号用于登录运营平台；员工档案用于归属探索记录、部门可见性和连接器鉴权。员工档案没有登录密码、Web 会话或自助账户页面。管理员本人需要体验探索时，也应使用绑定本人员工档案的普通 MCP 令牌，不能把管理员会话交给 WorkBuddy。

| 操作 | 员工（仅 WorkBuddy） | 管理员（Web 运营平台） |
| --- | --- | --- |
| 登录 SkillHive Web | 不允许，无个人登录流程 | 允许，管理权限校验 |
| 使用全员可见技能、查看本人探索 | 通过 MCP，按员工身份隔离 | 不提供个人工作台；试用需另用员工身份 |
| 保存、提交、继续或放弃本人探索 | 通过 MCP | 不替员工修改或提交 |
| 查看员工已保存的未提交草稿 | 仅通过 MCP 查看本人草稿 | 可以查看全文和修订历史，但不能修改、提交或放弃 |
| 查看正式提交及评审意见 | 通过 MCP 仅查看本人记录 | 可查看公司正式需求与历史提交快照 |
| 查看提交后的未提交修改 | 通过 MCP 仅本人可见 | 可以查看，但评审仍绑定最近正式提交版本 |
| 发布、激活规则及管理连接器 | 不允许 | 允许 |
| 维护员工档案、发放/轮换/吊销令牌 | 不允许，自助网页不提供 | 允许，记录操作人和交付对象 |
| 评审正式需求、查看运营统计 | 查询本人评审状态 | 公司范围，按业务职责使用 |

“管理员可见”不等于“其他员工可见”，也不等于“管理员可以代员工操作”。MVP 由管理员承担发布、接入运营和业务评审；后续若需细分权限，只在管理员运营体系内增加权限，不恢复员工个人 Web 工作台。

现有 `member` / `publisher` 身份不再允许进入 Web；不得为保留旧入口自动将其升级为管理员。历史发布者归属保留，既有 CLI 发布权限如需保留必须与管理员 Web 会话分离，不因 CLI 登录取得运营平台访问权。

公司服务器运维人员可能具有数据库访问能力，应通过运维制度单独约束；产品权限不承诺对数据库超级用户的绝对隔离。

### 5.2 员工档案与令牌生命周期

- 管理员创建员工档案，使用唯一手机号标识，维护姓名、部门、启用状态；这些信息不从模型自报姓名或 WorkBuddy 昵称推断。
- 每枚新令牌只绑定一个员工主体；建议按设备分别发放，权限为 `skills:read`、`explorations:read:self`、`explorations:write:self`，不具备任何 Web 管理权限。
- 明文仅在生成时向管理员展示一次，由管理员通过公司批准的私密渠道定向交付本人；数据库只存令牌哈希。禁止群发、公开表格、讨论正文或日志传递令牌。
- MVP 采用人工定向交付，不假定已集成企业 IM、邮件系统或自动发放服务。系统不记录交付方式和时间，也不在数据库保存令牌明文。
- 新令牌默认有效期建议 90 天，支持提前轮换；丢失或人员离职时先吊销。换设备可另发令牌，记录仍归同一员工，不因轮换创建新身份。
- 员工停用后，其全部新旧接入凭证立即停止访问。恢复员工时不复活已经吊销的令牌。
- 每次调用重新检查员工状态、凭证、权限和对象所有权。身份记录必须包含令牌引用，不能只验证服务间内部令牌。

Bearer 令牌识别的是持有该凭证的调用，不能证明实际操作者必定为员工本人。管理员在发放时接触过明文，应限制发放权限、保留审计；MVP 不把此身份机制宣传为不可抵赖签名。

## 6. 员工完整使用流程

### 6.1 首次接入

1. IT 在连接器包中预置公司服务地址并完成发布验证；管理员准备员工档案、正式连接器入口和 WorkBuddy 安装条件，不创建员工 Web 登录账号。
2. 管理员为该员工发放专属令牌，并通过受控公司渠道定向交付。
3. 员工通过公司提供的官方入口安装/启用 SkillHive 连接器，仅填写一次收到的专属令牌，不填写服务地址，也不打开 SkillHive 登录页。
4. 调用只读状态检查，确认企业名称、当前员工、服务兼容性及探索权限。
5. 员工说“帮我探索一个业务需求”，或者选择连接器提供的需求探索入口。

不将“管理员发放了令牌”当作“员工已连接”。运营平台如展示状态，只能写“最近成功连接时间”，不能据此宣称客户端当前在线。

首次接入完成后，日常使用与普通业务规则更新不要求重复安装连接器、输入令牌或配置地址。令牌到期、被吊销、凭证丢失或更换设备时联系管理员补发/轮换。已经使用手动 MCP 配置的员工迁移到公开市场连接器时完成一次验证，避免同时启用重复入口；不假定客户端会自动迁移旧凭证。

身份认证用于确定员工主体、记录归属和权限。本期通过管理员建档和令牌发放完成，不建设员工个人登录或 OAuth 回调页面。

### 6.2 开始探索

随后确认员工要新建还是继续已有探索。新建调用 `start_exploration`，成功后取得记录编号、规则版本、输出字段说明和保存策略；在确认服务器可用前不声称已开启自动归集。

### 6.3 探索阶段与讨论质量

| 阶段 | 讨论目标 | 阶段成果 |
| --- | --- | --- |
| 明确问题 | 从具体事件定位不便，而非直接接受解决方案 | 问题描述、具体例子、受影响对象 |
| 理解现状 | 确认当前流程、参与者、频率和已有替代办法 | 当前流程、痛点与已有依据 |
| 确认目标 | 区分必需目标、可选愿望和不做事项 | 目标、范围、非目标 |
| 明确约束 | 讨论权限、数据、资源、时间和风险 | 约束、风险、待确认事项 |
| 形成需求 | 用可理解、可评审的结构复述 | 收益、验收标准、最终总结 |

将上述讨论目标组织为动态决策树。每轮提出当前 frontier 中所有前置条件已明确且彼此不依赖的问题，不设置固定问题数量；员工回答后重新计算 frontier。问答优先使用 WorkBuddy 原生 `AskUserQuestion` / `AskQuestion` 弹窗：互斥答案单选，可同时成立的答案多选；需要描述经历或证据时保留自由文本，原生交互不可用时降级为同一消息内的编号文本问答。弹窗容量不得成为固定截断 frontier 的理由。先理解问题，再讨论可能方案；不得强迫员工提供其不知道的业务数据。未知项进入待确认清单，不虚构金额、频次、用户规模或承诺。

### 6.4 阶段保存与最终提交

- 完成一个有实质变化的阶段时调用 `save_exploration`，保存结构化总结，不上传整个聊天上下文。
- 收到保存回执后才提示“草稿已保存”，同时展示探索编号及继续探索提示。
- 员工要求“结束并提交”或确认最终总结后，入口 Skill 调用 `submit_exploration`；员工无需复制粘贴到另一个表单。
- 员工仅说“先到这里”“下次继续”时保存草稿，不推断为正式提交。
- 工具成功后在 WorkBuddy 展示需求编号、提交版本、提交时间，以及“待评审/待补充”等实际状态，不返回要求员工登录的管理端详情链接。
- 缺少关键内容时指出具体缺项并继续讨论；允许不确定内容进入待确认清单，但不得用空洞占位文本伪装完整。

阶段性总结可以按规则自动保存；最终提交意图仍需清晰。员工在 WorkBuddy 中查看总结并表达提交意图，由 AI 调用工具完成。记录标注“通过员工凭证由 AI 提交”，不再设置需要员工网页登录处理的“待本人核对”状态，也不把模型判断标为独立验证的本人签署。

员工可在 WorkBuddy 查询某次正式提交的具体内容；发现不准确时继续讨论并提交新修订。若业务需要正式签署，走公司既有审批流程并另行记录，不以管理员点击核对或模型传入的标志冒充员工确认。

### 6.5 WorkBuddy 内继续、查询与补交

员工可用记录编号继续，也可通过 `list_my_explorations` 查找本人记录。继续时通过 `get_exploration` 的 `activeRevision` / `activeContent` 加载服务器当前有效总结和锁定规则，不承诺恢复没有保存的原始对话。正式提交后的未提交修改被明确放弃时，历史修订仍供审计，但有效内容回到最近正式提交。

发生回传失败时，员工在 WorkBuddy 要求“查询刚才是否保存成功”或“继续编号为……的探索”，读取最后成功修订，再补充和重新提交。没有任何保存记录时，只能从仍在本机对话中的内容恢复，不能凭空还原丢失内容。

服务持续不可用时停止重复写入，保留客户端中仍可见的总结并联系管理员；恢复后回到 WorkBuddy 补交。MVP 不提供网页替代提交，不承诺断网后的后台补传。管理员只能排障、补发令牌或处理停用，不能代员工编辑草稿或提交需求。

已提交需求需新增修订，不能无痕覆盖正式快照。员工可通过 `get_exploration` 查询本人需求的评审状态和面向提交人的补充要求；平台不具备本期主动推送承诺，可由管理员通过公司渠道提醒员工回 WorkBuddy 查询。

### 6.6 目标对话示例

以下仅说明目标体验，不是实际测试记录：

1. 员工：“每月汇总部门报表太麻烦，帮我探索这个需求。”
2. AI 成功启动探索后：“目前最耗时的是收集、检查，还是合并？能举一个最近的例子吗？”
3. 员工：“主要是版本混乱，最后还要反复向各组确认。”
4. AI 继续澄清具体流程、频率和影响，阶段保存成功后提示“问题背景已保存为草稿”。
5. 讨论充分后，AI 展示结构化需求并询问是继续补充还是提交；员工：“就按这个提交。”
6. AI 保存最终版本并提交，收到服务器回执后展示需求编号及版本：“已进入需求池，待评审。之后可以直接问我‘查看这条需求的进展’。”

例子中的报表只作为业务描述，本期不会因此自动扫描或上传员工的 Excel 文件。

## 7. 回传内容与业务数据规则

### 7.1 结构化需求内容

| 字段 | 草稿要求 | 提交要求 |
| --- | --- | --- |
| 标题 | 可使用临时标题 | 1—128 字，能表达问题 |
| 问题描述 | 可空 | 必填，描述现状中的具体问题 |
| 目标用户/受影响对象 | 可空 | 必填，可用岗位或群体，不强制个人信息 |
| 当前流程 | 可空 | 必填；新业务可以明确说明尚无流程 |
| 痛点与事实依据 | 可空 | 至少一个痛点；依据区分员工陈述与待验证信息 |
| 目标与预期收益 | 可空 | 必填；允许定性收益，不要求编造数字 |
| 需求范围与非目标 | 可空 | 至少明确本次范围，非目标可为空 |
| 验收标准 | 可空 | 至少一条可检查的条件 |
| 约束与风险 | 可空 | 未知时明确列入待确认，不强制编造 |
| 待确认事项 | 可空 | 允许为空，存在时逐项列出 |
| 总结 | 可空 | 必填；与结构化字段一致 |

单次内容载荷建议上限 64 KiB（UTF-8），单个长文本字段 8,000 字，各列表最多 20 项；本期不包含文件附件。提交校验使用固定 Schema，AI 文本不能修改校验和权限规则。

### 7.2 系统记录字段

由服务端生成或核验：探索 ID、可读编号、员工 ID、创建时部门快照、技能 ID/版本、规则内容摘要、Schema 版本、修订号、状态、时间、当前令牌引用、幂等键、正式提交版本及审计事件。

部门快照只用于归属统计，不作为当前权限依据。显示身份从员工档案取值，不依赖员工 Web 账号；模型不得冒充其他员工，客户端名称等自报信息只能用于辅助分析，不能用于鉴权。

正式提交快照不可变。草稿保存形成修订；管理员可查看每个成功保存的草稿修订和正式快照。每次提交记录所用员工凭证、内容摘要及提交来源；不存储一个由模型或管理员填入即可生效的“本人已签署”标志。

## 8. 生命周期与评审

将“探索记录”和“需求评审”分开管理，避免“讨论结束”被误解为“需求已采纳”。

| 对象 | 状态 | 可执行动作 |
| --- | --- | --- |
| 探索 | 讨论中 | 本人继续、保存、提交、放弃 |
| 探索 | 已提交 | 查看提交回执；本人发起新修订 |
| 探索 | 修改中 | 继续保存；原正式快照仍可供评审查看 |
| 探索 | 已放弃 | WorkBuddy 内本人查看；MVP 不自动恢复，重新开始需新建记录 |
| 需求 | 待评审 | 管理员开始评审、要求补充或给出结论 |
| 需求 | 待补充 | 员工修改并重新提交后回到待评审 |
| 需求 | 评审中 | 管理员记录意见并给出结论 |
| 需求 | 已采纳 / 暂缓 / 不采纳 | 必须记录理由；不表示已开发或已交付 |

放弃是可审计的状态变更，不等于物理删除。技能停用是探索写入阻断原因，不改变既有正式需求的评审结论。

首次提交前放弃探索进入“已放弃”；已经正式提交后，放弃未提交修改仅结束当前草稿修订并返回“已提交”，原需求和评审记录不删除。管理员不能通过运营平台代替员工执行上述动作。

管理端状态变更校验允许的状态流转。评审操作带所评审的提交版本与评审修订号；员工已提交新版本时拒绝对旧版本直接覆盖结论，并提示刷新。

员工重新提交时保留历史评审意见，当前需求回到“待评审”，不自动继承旧版采纳结论。管理员可以看到员工正在修改的草稿，但评审操作只能选择正式提交快照，不能把未提交草稿作为评审版本或覆盖既有结论。

## 9. MCP 工具契约

现有 5 个技能读取工具保持兼容。以下工具负责员工的全部探索业务，包括查询、恢复和放弃；管理员跨员工查询和评审不暴露给员工侧连接器。

| 工具 | 主要入参 | 主要返回 | 行为 |
| --- | --- | --- | --- |
| `get_connector_status` | 客户端/入口协议版本（可选） | 企业名称、员工身份、权限、激活规则版本、支持的协议 | 只读；不返回凭证或内部秘密 |
| `start_exploration` | 初始问题、幂等键、入口协议版本 | explorationId、编号、锁定规则、资源清单、revision | 验证员工状态和令牌权限后原子创建；规则由服务器选择 |
| `list_my_explorations` | 状态、关键词、分页 | 本人记录摘要 | 默认不返回全文；不接受任意 userId |
| `get_exploration` | explorationId、提交版本（可选） | 本人当前有效草稿/正式快照、规则版本、状态、activeRevision、面向本人的评审反馈 | 员工侧只读本人记录；恢复探索或查询正式版本，不含内部运维备注 |
| `save_exploration` | explorationId、expectedRevision、内容、幂等键 | 新 revision、savedAt、内容摘要、继续探索提示 | 保存完整结构化草稿快照 |
| `submit_exploration` | explorationId、expectedRevision、幂等键 | requirementId、编号、submittedRevision、submittedAt、评审状态 | 提交指定已保存版本，创建不可变快照 |
| `abandon_exploration` | explorationId、expectedRevision、幂等键 | 状态、revision、保留的正式提交版本（如有） | 按第 8 节放弃初始探索或未提交修改，须先确认员工意图 |

最终提交不附带一份可能不同于已保存版本的新内容；如果有修改，先保存，再提交该 revision。员工工具回执不返回管理端详情链接、免登录访问链接或登录凭证，只返回可用于 MCP 查询的编号、状态、版本和继续操作提示。管理端链接仅在管理员 Web 中使用。

工具权限按员工令牌用途检查，不能仅依赖客户端是否展示某个工具。`allowed-tools` 或 Skill 中的限制是使用说明，不替代服务器鉴权；不增加让 AI 自行授权、发放令牌或确认电子签署的工具。

需求探索规则属于应用 Skill，不属于普通 Skill，也不会出现在 `list_skills`、`search_skills` 或动态 Prompt 中；通用 `get_skill` 和普通资源接口拒绝读取它。企业 Skill 助手从独立应用目录发现需求探索后，必须先调用 `start_exploration` 或 `get_exploration` 获得本人记录及锁定规则。读取规则资源时，`get_skill_file` 必须同时携带该员工自己的 `explorationId`，并且 slug、版本和路径都要与服务器保存的锁定快照一致。这样管理员发布但尚未激活的新版本不会被旁路加载，旧探索也不会在讨论中途换版。

### 9.1 写入一致性

- 幂等键按员工、操作和目标隔离；相同键及相同请求返回原结果，同键不同请求返回冲突。
- 幂等结果与业务写入在同一事务提交，不能先显示成功再异步落库。
- `expectedRevision` 实现并发控制；另一 WorkBuddy 对话或设备已修改时，返回冲突并要求重新读取，不覆盖较新内容。
- 首次正式提交、后续提交与需求版本建立唯一约束；不同幂等键也不能把同一探索修订重复提交为多条正式版本。
- 幂等记录保留至少 7 天；即使过期，同一探索修订的提交唯一性仍由持久业务约束保证。超出窗口的新建重试须先查本人记录，避免重复探索。
- 写操作收到超时不等于写入失败。先用原幂等键重试或查询记录确认；不得立刻生成新键重复新建。
- 错误返回机器可读错误码、可读原因、是否可重试和下一步；不输出内部堆栈或敏感信息。

建议错误码覆盖：未认证、令牌权限不足、对象不存在/不可见、规则停用、协议不兼容、内容校验失败、修订冲突、限流和暂时不可用。对他人记录统一返回不存在，避免泄漏其存在性。

## 10. 自动化边界与异常体验

MCP 服务只能处理实际收到的工具请求，无法可靠观测员工是否仍在聊天，也不能保证模型每轮调用保存工具。本期的自动化目标是：正常受支持流程中自动调用保存/提交，收到请求后可靠落库，失败可见且可恢复。

| 情况 | 系统与 Skill 应有行为 | 禁止的表达或行为 |
| --- | --- | --- |
| 未安装/未授权 | 提示从公司入口启用连接器，向管理员领取令牌 | 要求员工注册/登录 SkillHive 或宣称全员已接入 |
| 预置地址不可达或配置错误 | 提示联系 IT，管理员修正部署或连接器发布配置 | 要求普通员工自行改地址，或改投不可信服务 |
| 错误、过期或吊销的令牌 | 拒绝读写，提示联系管理员补发/轮换 | 退回匿名写入、共享管理员令牌或个人领令牌网页 |
| 员工拒绝保存工具调用 | 停止回传并说明结果未保存 | 绕过确认、通过其他通道上传 |
| 模型未调用保存 | 服务器仅显示已有记录/保存时间 | 用技能调用次数推算保存成功 |
| 客户端退出或电脑离线 | 仅保留已成功保存内容，之后可继续 | 声称有后台离线队列自动补传 |
| 请求超时、回执丢失 | 在 WorkBuddy 按幂等规则重试或查询状态，持续失败联系管理员 | 未获回执即显示已提交，或跳转个人网页补交 |
| 多端修订冲突 | 重新读取并让员工确认合并内容 | 静默覆盖最新草稿 |
| 服务暂不可用/限流 | 展示重试建议和最后成功记录 | 无限重试或循环新建记录 |
| 规则发布新版本 | 新探索用新版本，老探索保持原版本 | 中途无提示替换规则 |
| 规则紧急停用或权限收回 | 阻止继续写入，保留本人可查的既有成果 | 借历史会话继续越权读取资源 |
| 最终内容不完整 | 返回缺项并继续讨论，保留草稿 | 自动编造缺失数据以通过校验 |

阶段保存是尽力触发，不是固定时间后台定时器。管理员可以查看已成功保存的草稿正文，并将超过一天未更新的记录标识为“尚未提交”，但不能推断其真实结束时间或自动提交；草稿不向其他员工公开。

## 11. 管理员运营平台页面设计

Web 仅面向管理员，保留管理员登录及会话安全，不将后台改成匿名访问。沿用 Vue 3 + Element Plus、已有应用壳层、路由标题、表单、表格、Markdown 安全渲染和全局样式 Token。

### 11.1 管理员登录与页面边界

- 登录页标注“管理员登录”，不提供员工注册、个人工作台、密码找回或个人令牌入口；管理员账号恢复由受控运维流程处理。
- 所有运营页面及对应 API 均校验管理员身份；不能只在前端隐藏菜单。非管理员的登录请求不签发 Web 会话，已有非管理员会话也不能访问运营 API。
- 员工专属令牌仅可用于 MCP，不可作为 Web Cookie、Web Bearer 会话或领取管理员会话的凭据。
- 旧 `/explorations` 等拟定个人页面不建设；旧员工市场、详情、许愿墙和接入设置入口改为管理员功能或关闭员工访问。
- 管理员登录入口不出现在员工连接器引导中；员工误入仅得到“此处为管理后台，请在 WorkBuddy 使用或联系管理员”的说明，不引导注册。

### 11.2 员工与接入凭证（拟 `/employees`、`/employees/:id`）

- 列表管理员工手机号、姓名、部门、状态和最近成功接入时间，不设置密码和 Web 角色。
- 令牌创建弹窗明确员工对象、设备备注、权限及有效期；明文仅显示一次，并提示定向交付。没有批量明文下载或公开分享链接。
- 提供轮换、吊销和停用员工；敏感操作需确认并审计，停用影响范围明确展示。
- 最近接入状态只根据成功请求更新，不以令牌已经生成或交付推断当前在线。

### 11.3 连接器与 Skill 运营（改造 `/settings`、Skill 管理页）

- 由管理员查看正式公司地址、平台 source、包版本、客户端兼容性、测试/生产环境和审核状态。
- 提供审核通过后的公开市场入口及可分发的非敏感使用说明；审核未完成时显示“待上架”。
- 员工说明仅介绍领取令牌、启用连接器和 WorkBuddy 用法，不提供员工网页登录步骤。
- “Skill 管理”提供“Skill 列表 / 发布 Skill”两个页签；发布时只选择普通 Skill 或应用 Skill，不指定所属应用。管理员可预览版本、设置部门范围，并在普通 Skill 详情页即时维护触发词；员工通过 WorkBuddy 查询和取用，不另建 Web 技能市场。
- 手动 MCP 配置只作为 IT 兼容/排障资料，地址自动带入，不嵌入通用共享令牌。

### 11.4 探索记录与公司需求池（拟 `/explorations`、`/requirements`）

- 仅管理员可进入；员工令牌、旧普通用户会话和未授权请求均不能读取管理端记录。
- “探索记录”展示全部已成功保存的草稿和正式提交；筛选员工、部门、探索状态、规则版本、更新时间和关键词。
- 草稿列表列：探索编号、标题、归属员工、部门、状态、规则版本、最后保存时间；详情可查看结构化草稿及修订历史。
- “公司需求池”只展示正式提交；筛选提交时间、部门、评审状态、规则版本和关键词。
- 正式需求列表列：需求编号、标题、归属员工、部门、评审状态、提交版本、提交时间和操作。
- 需求详情展示结构化正式版本、提交来源和评审历史，并提示是否存在更新但未提交的草稿；不显示虚假的“本人已签署”。
- 管理员可要求补充、采纳、暂缓或不采纳，写明面向员工的理由；内部运营备注与员工可见意见分开存储和返回。
- 草稿详情只读，不提供代员工修改、提交、放弃或本人核对按钮；员工补充始终回到 WorkBuddy。
- 不向员工开放需求网页、公开分享或免登录详情链接，不默认加入旧许愿墙投票。

### 11.5 应用、连接器、监控与审计

- “应用”列表展示需求探索等具有完整业务闭环的内置应用；“Skill 管理”通过“Skill 列表 / 发布 Skill”两个页签管理 Skill，其中列表只展示普通 Skill。
- “应用 > 需求探索”独立维护应用触发词，并从满足需求探索契约的应用 Skill 候选池中选择当前运行 Skill，再选择运行版本和应用启停；应用与 Skill 的唯一关联就在这一步建立。Skill 内容与资源使用“Skill 管理 > 发布 Skill”维护，历史版本禁用收纳为低频应急设置。发布与激活保持两个明确动作。
- “WorkBuddy 连接器”独立展示连接器包、企业地址、服务端协议、平台审核和实测客户端版本，避免与业务规则混淆。
- 管理员可停用应用入口或禁止危险版本；激活前说明只影响新探索。
- 监控默认展示员工手机号、探索编号、状态、规则版本、最后保存时间、错误码和计数；管理员需要查看内容时进入有审计记录的探索详情，不在监控列表铺开正文。
- 草稿正文从探索详情读取，正式需求从需求池读取；运营统计只给聚合结果，不因导出统计而复制全部正文。
- 审计涵盖管理员登录、员工维护、令牌发放/吊销、规则激活和评审，不记录令牌明文或需求正文。

### 11.6 统一界面要求

列表使用全宽内容面板，筛选紧凑靠左、主要操作靠右，标题列弹性填充；不增加无意义的窄宽度限制，不使用原生 table 替代已有表格组件。

所有页面覆盖加载、空数据、错误重试、成功、无权限与不可用状态。页面标题只出现一次并有路由元数据；无权限写操作不渲染，字段读取权限在服务端和界面同时控制。

表单具有清晰标签、必填和字段错误；可选字段清空显式传 `null` 或约定空值。弹窗支持键盘和焦点管理；图标按钮具有可访问名称；状态用文字而非仅靠颜色。状态冲突、保存失败必须说明对象、原因和下一步。

## 12. 服务与数据架构

### 12.1 责任划分

| 组件 | 本期职责 |
| --- | --- |
| WorkBuddy 连接器 | 安装配置、载入入口 Skill、发起 MCP 请求和展示对话 |
| MCP Server | 暴露探索工具、校验协议输入、传递可信身份、返回明确回执 |
| Registry | 管理员/员工两类身份鉴权、草稿与正式内容查询、规则选择、数据校验、状态机、事务保存与审计 |
| PostgreSQL | 不可变版本、探索修订、正式快照、幂等约束与审计持久化 |
| Console | 仅管理员登录；内置应用运营、普通技能发布、员工档案/凭证、草稿查看、正式需求评审、连接器状态和监控 |

员工请求通过经 IT 人工确认的企业 MCP 入口到 MCP Server，再由服务端内部身份链路调用 Registry。Web 只有管理员会话，其 API 可读取已保存草稿、管理配置/员工并评审正式提交，但不提供员工自助探索写入，也不提供管理员代员工写入。两类身份、入口和允许操作严格分开，不混用员工令牌与管理员 JWT。

Registry 必须同时验证启用中的员工主体及对应接入令牌。实现已将 `CallerIdentity` 扩展为员工主体与旧只读主体，不能靠给员工开放 Web 账号来满足旧代码结构；探索工具的错误回执使用员工可理解的错误码、原因和恢复建议。

### 12.2 数据对象

- `skills.skill_type`：`ordinary` 表示可供企业 Skill 助手检索的普通 Skill；`application` 表示只进入应用候选池。具体应用与当前 Skill 版本的关联由应用运行策略维护。
- `skills.trigger_phrases`：普通 Skill 的即时发现配置，不随不可变版本发布；应用 Skill 保持为空。
- `application_discovery_configs`：内置应用的即时发现配置，与应用运行规则和关联的应用 Skill 版本解耦。
- `exploration_policy`：建立需求探索应用与兼容应用 Skill 的关联，并维护激活版本、功能开关与禁止版本；只能引用通过需求探索契约校验的已发布应用 Skill 版本。
- `employees`：唯一手机号、姓名、部门和启用状态，不含登录密码、Web 角色或历史账号映射；迁移前存量员工允许暂时缺少手机号，但编辑时必须补齐。
- `employee_tokens`：令牌哈希、员工引用、用途范围、到期/吊销时间、签发管理员和设备备注。
- `explorations`：所有者、部门快照、锁定规则版本、当前状态和修订指针。
- `exploration_revisions`：内容 Schema、结构化总结、作者、创建时间和内容摘要。
- `requirements` / `requirement_submissions`：每个探索对应一个需求，保存各次正式提交及当前指针。
- `requirement_reviews`：正式版本评审与面向员工的反馈；不再设计个人网页核对记录。
- `idempotency_records` / `exploration_audit_events`：可恢复写入结果及业务审计。
- 旧 `user_tokens` 保留必要的只读兼容与员工映射，不继续向员工开放自助创建 API；新员工令牌与管理员账号凭证区分用途。

具体物理表可在技术设计中合理合并，但不能丢失所有权、不可变提交、并发版本及幂等约束。不得把需求正文塞入通用 usageEvents，也不得直接沿用许愿墙的全员查询 API。

当前技能版本引用存在级联删除关系；探索引用规则后，需限制被引用版本删除或保留独立规则快照，保证历史可追溯。本方案要求至少保留当次规则内容摘要及可恢复的版本内容。

### 12.3 接口分组

- 管理端统一使用 `/api/admin/*`：员工/凭证、归集核验、技能规则、草稿只读查询、正式需求评审、监控与审计，均需管理员会话。
- MCP 内部使用独立内部路由组提供本人探索的创建、读取、保存、提交、放弃及反馈查询，强制服务身份与员工令牌双重验证；不接受管理员会话代替员工身份。
- 员工对外仅访问 MCP 端点；不提供员工 Web 登录、个人探索 REST 接口、凭证换管理员会话或免登录详情接口。
- 管理员登录、退出、会话检查保留独立认证入口；旧运营 API 必须纳入同样的管理员权限边界，不能仅新增安全路由而留下旧入口绕过。

这些路径已按本节边界实现；正式兼容性仍以真实 WorkBuddy 客户端和平台审核结果为准。

## 13. 安全、隐私与数据治理

### 13.1 采集和外发边界

仅归集员工主动开展的企业需求探索总结、必要元信息和正式提交。入口不得主动读取无关聊天、联系人、任意本地文件或其他员工记录。

WorkBuddy 参与对话意味着技能内容和员工输入可能进入其运行环境及模型处理流程；公司服务器存储结果不等于“全程不出公司”。正式推广前由公司确认平台使用条款、数据处理方式及允许输入的数据等级。

员工令牌的存储方式不能推导业务内容不外发。入口 Skill 必须提醒不要输入密码、密钥、非必要个人信息或未经批准的敏感资料；简单提示和规则校验不能被宣传为完备 DLP。

### 13.2 技术与操作控制

- HTTPS、最小权限、持续吊销检查；保护内部共享令牌，不在客户端分发。
- 以服务端身份和对象所有权为准；模型输出、用户文本、资源内容均视为不可信输入。
- 不接受从讨论文本传入任意保存 URL、SQL、脚本或目标员工 ID。
- 服务端 Schema 校验，限制正文和列表大小；列表分页、搜索限流，避免全量导出。
- Markdown 安全渲染，禁止执行原始脚本；日志默认只记录 ID、状态、耗时和错误码，不记录正文或凭证。
- 所有 Web 业务 API 强制管理员授权并保护会话、校验跨站请求；员工令牌和旧普通用户会话不得绕过边界。仅隐藏按钮或删除员工登录页面不能替代服务端限制。
- 管理端展示过令牌明文意味着管理员具备短暂接触凭证的能力，应限制签发人、清除前端展示状态并禁止日志、批量导出；不会因“不提供员工登录”就改用匿名或共享身份。
- 草稿/正式内容详情查看、评审、规则激活、令牌权限修改和数据清理均留审计；MCP 不提供越权审批或批量删除工具。
- 首次试点使用脱敏案例；数据库备份和恢复演练包括新增表与审计数据。

### 13.3 保留与删除

试点建议：未提交草稿在最后更新后保留 90 天，已提交成果保留 365 天；这是待公司批准的产品默认建议，不是平台或法律要求。

正式启用前明确保留期限、责任人、公司现有的员工联系/删除申请渠道、审批流程及备份到期规则；不为此新建员工 Web 登录入口。员工可在 WorkBuddy 查询本人记录，停止、删除或服务不可用时通过既有公司渠道联系管理员。MVP 至少交付可审计的运维清理流程；自动清理任务可后续实现，但不能在没有可执行清理流程时承诺到期自动删除。

吊销某令牌停止该令牌调用，停用员工停止该主体全部访问；均不自动抹除已提交的公司业务记录。通过公司渠道受理删除请求；执行删除时同步处理修订、幂等响应中可能存在的内容及规则快照，保留不含正文的必要审计。历史备份按批准的到期策略淘汰，不能承诺即时从所有备份消失。

仓库清理命令支持“按保留期批量清理”和“按删除申请精确清理单个探索”两种模式；两者默认只预览，实际执行都要求记录审批人，删除申请模式还必须记录不含业务正文的申请单号，并以探索 UUID 的 SHA-256 指纹保留最低限度的目标可追溯性。具体命令和安全边界见上线与回退手册第 7 节。

## 14. 指标与验收标准

### 14.1 指标口径

- 接入成功：员工凭证状态检查通过且具备探索权限；不是管理员发放令牌的次数。
- 探索启动：服务器成功创建 exploration；无法统计从未触发工具的自然语言意图总量。
- 保存成功：产生持久修订并可重新读取；不是模型说“已保存”的次数。
- 正式提交：产生唯一正式快照；业务评审通过另行统计。
- 完成率：在同一启动时间队列中，有至少一次正式提交的探索数 / 成功启动的探索数；以 explorationId 去重。
- 技能读取量：沿用既有统计，与探索完成率分开展示。
- 需求质量：由人工抽样评价问题清晰度、事实依据和验收可检查性，不仅依赖字段非空。

不设置基于本系统“全公司真实讨论漏采率为零”的指标，因为 MCP 服务看不到未触发工具的讨论。

### 14.2 MVP 验收用例

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| A01 | 无员工网页登录接入 | 管理员建档并定向发令牌；员工仅在 WorkBuddy 填令牌，无需 SkillHive 注册/登录、填写地址或编辑 JSON |
| A02 | 全员可用 | 两个部门的普通员工都可启动全员规则；受限技能仍按原权限过滤 |
| A03 | 获取当前规则 | 缺少或未完整声明 Grill Me 协议的应用 Skill 不进入候选；仅发布未激活 V2 时不切换；激活后新探索用 V2，旧探索保持 V1；无需重新安装、输入令牌或配置地址；官方及兼容入口一致 |
| A04 | 正常讨论 | 按动态决策树询问完整当前 frontier，不限制每轮问题数量；至少完成一次阶段保存与最终提交，服务器内容和回执编号一致 |
| A05 | 直接接入 | 有效员工令牌具备所需范围时可以开始和保存探索，不依赖额外归集告知或确认状态 |
| A06 | 手机号身份与轮换 | 新建员工必须使用唯一有效手机号；旧用户 PAT 不能接入 MCP；员工令牌写本人记录，轮换不改变记录归属 |
| A07 | 对象权限隔离 | A 员工无法读写 B 的记录；管理员可读取全部已保存草稿和正式提交，但不能通过 Web/API 替员工编辑、放弃或提交 |
| A08 | 到期、停用和吊销 | 长连接中令牌到期/吊销或员工停用后仍拒绝调用；恢复员工不复活吊销令牌 |
| A09 | 超时与重复 | 模拟落库后断开响应，原键重试返回原结果，无重复探索/提交 |
| A10 | 并发修改 | 两端以同一旧 revision 保存，仅一个成功，另一端明确冲突 |
| A11 | 中途退出 | 重新接入可恢复最后成功总结；明确不恢复未保存聊天 |
| A12 | WorkBuddy 内恢复 | 在 WorkBuddy 查询保存结果、恢复、补充并重新提交；也可明确放弃草稿；不出现个人网页登录或详情链接 |
| A13 | 草稿与正式版本 | 管理员能查看员工各次已保存草稿；评审只能绑定正式快照，草稿变化不覆盖或改变既有评审 |
| A14 | 评审版本冲突 | 新提交到达后，旧评审操作被拒绝；历史意见保留 |
| A15 | 管理员 Web 边界 | 员工令牌、旧 member/publisher 会话和 CLI 凭证都不能访问运营 API 或换取管理员会话；管理员仍需正常登录 |
| A16 | 紧急回退 | 规则回退只影响新探索；停用可阻断危险版本写入；当前激活版本被禁止时管理端显示不可运行、企业应用目录不再返回入口；已存数据仍可查 |
| A17 | 客户端兼容 | 声明的最低版及至少一个当前稳定版实测；记录操作系统和安装包版本 |
| A18 | 凭证与回执安全 | 员工连接器令牌一次展示、哈希存储、定向交付并审计；个人 PAT 签发、查询和吊销入口不存在；包/日志无秘密，员工回执无管理端或免登录详情链接 |
| A19 | UI 与接口质量 | 页面完整状态、路由标题元数据、权限和键盘操作通过检查，内容区不重复显示页面级标题；相关 lint/typecheck/test/build 通过 |
| A20 | 持久化与发布 | 重启服务后修订和回执仍可查；备份恢复成功；市场审核通过与企业端连通分别有证据 |

试点建议覆盖至少 20 名员工、2 个部门和 50 次受支持的标准探索流程。正常流程自动产生有效提交的比例目标不低于 95%，异常时必须提示未保存/未提交及恢复步骤；服务恢复且内容仍可获得时，应能在 WorkBuddy 内补交。这是试点门槛，不是对任意自由对话或已丢失内容的保证。安全越权、假成功、重复正式提交为零容忍项。

服务性能目标：在 20 个并发客户端的测试条件下，探索读写服务端响应 P95 不超过 3 秒，不含模型推理和公网传输；实施时记录数据量、环境和持续时长，未压测不得宣称达标。

## 15. 分期交付与迁移发布

### M0：接入与行为验证

交付：预置测试服务地址的连接器包原型、脱敏入口 Skill、管理员发放的测试员工令牌、仅含令牌输入项的表单、协议兼容检查和测试记录。

验证重点：无员工网页登录的发放与连接流程、无地址输入体验、入口 Skill 被识别、Streamable HTTP 认证、自然语言触发读写工具、工具确认和 WorkBuddy 内恢复。用真实受支持客户端验证，不以工具单测代替端到端证据。

同时向平台确认标识、上架类别、审核资料、企业私有访问要求和当前版本基线。M0 不能证明全员统一下发，也不以此为本期承诺。

### M1：闭环 MVP 与正式接入

交付：管理员专用 Web 及 API 权限收敛、员工档案与令牌发放、探索工具和持久化、规则锁版、公司需求池、评审、WorkBuddy 内查询/补交、监控审计、运维说明和正式审核包。

达到 A01—A20 后再向目标企业全员推广。开发完成、平台审核并公开上架、公司服务器部署成功和目标企业员工实测通过是四个独立检查项；其中任意未完成，都不得宣布连接器升级已在目标企业全量完成。市场公开可见仅表示可发现和安装，不表示任意 WorkBuddy 用户可以访问企业数据。

### M2：推广与效率优化（另行立项）

候选能力：企业身份提供方授权、管理员分级运营权限、企业统一配置能力、附件、语义去重、聚类报告、提醒通知、自动数据清理。

未来如需替换人工发放/填写令牌，可另行评估由企业身份提供方完成的 OAuth 等方案，但不默认恢复 SkillHive 员工个人登录。公开市场连接器不会自动提供员工实名映射。完整聊天持久化属于新的架构需求，不以此在本期增加员工 Web 讨论页面。

### 15.1 迁移和上线顺序

1. 备份并验证现有数据，盘点管理员账号、普通用户/发布者、旧会话、CLI 凭证和 PAT；不删除历史技能、许愿或使用记录。
2. 新增员工主体和令牌结构，由管理员为存量员工补齐唯一手机号；重名不能自动合并，无法确认手机号的记录保持待补充状态。
3. 旧用户 PAT 不再接受为 MCP 凭证；新探索只绑定员工主体和员工连接器令牌。
4. 部署管理员登录和全量 Web/API 权限收敛，撤销非管理员 Web 会话，关闭员工自助令牌、个人页面和旧公共业务入口。保留的 CLI 发布认证须与 Web 会话隔离，不能成为旁路。
5. 配置公司探索规则，管理员为试点员工定向发放新令牌；员工无需创建个人 Web 密码。
6. 验证 `/sse` 与 `/mcp`、两个员工相互隔离、管理员访问边界，以及 WorkBuddy 内完整查询/提交/恢复。
7. 将批准的生产服务地址预置到正式包，核验环境隔离后实测和审核；员工只填写管理员发放的专属令牌。
8. 扩大试点、复核指标与数据政策，再开放全员使用。

### 15.2 回退规则

出现安全或数据一致性问题时，优先关闭探索写入与新建开关，保留有权限的 MCP 技能读取/本人结果查询，以及管理员对正式结果的运营查询。保留员工已提交数据，不以回滚数据库结构的方式丢弃成果，也不通过恢复旧员工 Web 登录绕过新边界。

规则问题回退激活版本；入口包问题修复并重新发布，不能假定市场包立即完成更新。服务端保留至少前一已发布入口协议版本的兼容；重大安全问题可明确拒绝旧协议并提供升级指引。

## 17. 方案结论与交付边界

本期升级的核心不是“把 MCP 配置换成公开市场安装入口”，而是交付一个由 SkillHive 第三方连接器触达的内置需求探索应用：公司规则可编辑并版本化发布，获授权员工按需取用，讨论成果结构化保存，正式结果进入受控需求池。

公开市场连接器是员工使用入口，SkillHive Web 仅是管理员运营平台；员工不注册或登录 SkillHive。连接器是否可见、是否安装与企业数据授权相互独立，服务端承担最终权限和保存事实，入口 Skill 承担讨论引导和工具调用约定。模型遵循约定属于可测试但不具备绝对保证的行为，因此回执、幂等、修订和 WorkBuddy 内恢复必须与正常流程一起交付。

仓库已完成本地 MVP：数据库迁移、管理员权限、员工档案与专属令牌、7 个 MCP 探索工具、草稿/提交/评审/审计闭环、连接器源包与构建校验均已落地，并由单元测试、生产构建和 PostgreSQL 端到端 smoke 覆盖。部署、激活、发放、验证、清理和回退步骤见[上线与回退手册](../operations/workbuddy-requirement-exploration-runbook.md)。真实企业地址、WorkBuddy 实机验证、平台注册/审核、生产部署、公司数据政策批准和员工试点仍是外部上线门槛，不能用本地测试结果替代。

A01—A20 的当前证据与缺口持续记录在[MVP 验收追踪表](../operations/workbuddy-requirement-exploration-acceptance.md)，不得仅凭本节的实现摘要关闭外部验收项。
