# WorkBuddy 需求探索上线与回退手册

适用范围：SkillHive 管理员运营平台、Registry、MCP Server、PostgreSQL，以及 SkillHive 公开市场第三方连接器。员工只在 WorkBuddy 使用需求探索，不登录 SkillHive Web。

## 1. 上线前门槛

正式上线前必须逐项确认并留存负责人、日期和证据：

- 公司批准的稳定 HTTPS 域名，外部完整入口为 `https://<企业域名>/mcp`；不得使用示例域名。
- TLS、反向代理、网络边界和 WorkBuddy 到该地址的可达性已验证；Registry 与容器端口不直接暴露到不受信网络。
- WorkBuddy 平台的连接器标识、个人开发者发布主体、服务类目“商业服务—企业管理”、公开市场可见范围、审核材料和目标客户端版本已确认。
- 市场详情、令牌输入说明和员工接入材料均明确“公开安装不等于企业授权”；无有效员工令牌时服务端不返回任何企业数据。
- 个人开发者发布主体、SkillHive 服务运营方、目标企业数据责任方之间的授权关系，以及隐私政策、服务协议、支持联系方式和删除申请渠道已经留存受控证据。
- 公司已经批准数据等级、未提交草稿和正式需求保留期限、删除申请渠道。
- 至少准备两个不同部门的测试员工，使用非生产敏感数据完成隔离和完整闭环验证。

## 2. 部署与迁移

先备份数据库并验证备份可以读取，再执行：

```bash
pnpm check
pnpm connector:validate
pnpm validate:production -- --env-file .env --phase deploy
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml ps
```

`validate:production` 不输出密钥值。部署联调使用 `deploy`，只检查弱或复用密钥、明文传输开关、显式配置但超范围的保留期，以及直接暴露的服务端口；未填写保留期时使用运行时默认值 90/365 天。该阶段允许企业名称和 WorkBuddy 连接器保持 `unconfigured`，因此代码部署不依赖平台发布准备。准备向目标企业全员推广时必须执行 `pnpm validate:production -- --env-file .env --phase launch`，再检查正式企业名、生产连接器标记、获批 HTTPS `/mcp` 地址、连接器元数据、平台审核、公开市场入口以及真实客户端版本、操作系统和实测时间。

仓库自动部署使用 commit SHA 镜像标签，在远端切换前以容器进程环境执行同一 `deploy` 门禁，并通过 Compose 等待 PostgreSQL、Registry、MCP 和 Console 健康。远端脚本维护一套 `rollback` 应用镜像：健康切换失败时恢复它并清理失败镜像；成功后保留新的当前版本和一套回退版本，清理更早的无用标签，避免版本标签持续占满磁盘。首次部署没有可恢复镜像时保持失败状态，由运维排查后重试。数据库迁移是前向操作，不能把镜像恢复误称为数据库回滚。

Registry 启动入口会执行 Drizzle 迁移。确认 `0007`—`0016` 已进入迁移日志，并检查健康端点：

```bash
curl --fail http://127.0.0.1:3001/health
curl --fail http://127.0.0.1:3100/health
```

生产部署至少包括不同的 32 字符以上随机 `SKILLHIVE_SESSION_SECRET` 和 `SKILLHIVE_INTERNAL_TOKEN`、强数据库密码及安全监听边界；保留期未填写时使用 90/365 天默认值。企业名称和连接器字段可以在代码部署后补充，未配置期间管理端显示未就绪，不能构建或发布正式连接器。确定正式地址后填写 `WORKBUDDY_CONNECTOR_MCP_URL=https://<企业域名>/mcp`；平台提交、审核、实测和市场入口状态分别记录在 `WORKBUDDY_CONNECTOR_*` / `WORKBUDDY_VERIFIED_*` 配置中。不要把 `.env`、员工令牌或内部令牌提交到 Git、连接器包或工单正文。

## 3. 规则上线

需求探索是内置应用，仓库提供应用可初始化的基线规则包 `examples/seed-skills/requirement-exploration/`。它与连接器中的企业 Skill 助手和需求探索快捷入口分别独立版本。部署后先验证仓库基线：

```bash
pnpm dev:cli -- validate "$PWD/examples/seed-skills/requirement-exploration/SKILL.md"
```

普通 Skill 和应用 Skill 使用同一上传发布入口，但只有管理员可以发布应用 Skill。发布时只选择用途类型，不选择具体应用，也不向 SKILL.md 写入应用标识。应用 Skill 先进入候选池；需求探索应用页只展示通过固定工具、讨论方法、结构化 Schema 和完整 `grilling-protocol.json` 契约校验的版本。随后按以下步骤操作：

1. 管理员进入“应用 > 需求探索”，首次部署点击“初始化系统基线”，生成 1.1.0 Grill Me 基线、结构化 Schema、机器可读访谈协议及第三方声明；该操作不会自动开放员工入口。
2. 管理员复核基线 Skill，或进入“Skill 管理 > 发布 Skill”，选择“应用 Skill”后上传完整 Skill 包；后续调整以新的语义化版本和变更说明再次上传，不直接改写已发布版本。
3. 回到应用页面，从通过需求探索契约校验的应用 Skill 候选中选择当前运行 Skill，再选择目标版本并保持停用；此步骤同时建立应用关联和运行指针。
4. 用测试员工完成状态、开始、按返回的 `explorationId` 读取锁定规则资源、完整当前 frontier 访谈、保存、查询和提交；确认入口不限制每轮问题数量，旧探索仍锁定旧规则版本，且缺少或错用 `explorationId` 不能读取受管规则资源。
5. 验证通过后启用应用。启用只影响新探索，不改写历史规则快照。

规则内容有问题时，将激活指针切回上一已验证版本；某个历史版本存在风险时将其加入“紧急禁止的规则版本”，其既有探索仍可读取但不能继续写入；影响范围不明确时直接停用全部探索写入。

## 4. 员工接入

每位员工必须单独处理：

1. 管理员以手机号建档并维护姓名、部门，不创建员工 Web 账号。手机号必须唯一；迁移前的存量员工若显示“待补充”，应先补齐手机号。
2. 为该员工签发有期限、最小范围的令牌。明文只显示一次，通过批准的私密渠道定向交付；系统不记录交付渠道或交付状态。
3. 员工从 WorkBuddy 公开市场安装经公司确认的 SkillHive 连接器，只填写专属令牌；无需填写服务器地址或登录 SkillHive。公开可见和安装成功不代表已经取得企业数据访问权限。
4. 员工在 WorkBuddy 调用状态检查，成功后才可记为最近连接；签发令牌不等于已连接。

遗失或到期时签发新令牌并吊销旧令牌。停用员工会吊销其全部令牌；恢复员工不会恢复已吊销令牌。

## 5. 正式连接器构建与验证

在隔离构建环境中使用获批真实地址：

```bash
pnpm connector:build -- https://<企业域名>/mcp
pnpm connector:verify
```

构建脚本会拒绝凭据、查询参数、IP、本机地址和 `.example` 等示例保留域名。产物目录、版本化 ZIP 和包外 SHA-256 清单位于 `integrations/workbuddy/dist/` 且被 Git 忽略；独立校验命令会再次核对 ZIP 摘要、精确文件集合、逐文件摘要和秘密扫描。也可由手动 GitHub Actions 工作流从受控 Secret 注入正式地址，生成保留 7 天的审核产物。上传前按[连接器提交与实测记录](./workbuddy-connector-submission-record.md)核对摘要，确认包内没有令牌、内部地址、测试正文或日志。必须在真实 WorkBuddy 客户端记录以下证据：

审核包由个人实名认证开发者提交到 WorkBuddy 公开市场。平台审核通过、市场公开上架、目标企业授权接入和目标企业全员推广是不同状态：公开市场允许所有用户发现和安装连接器，但服务端只向持目标企业有效员工令牌的请求返回数据。市场页不得使用“WorkBuddy 官方连接器”等可能暗示平台运营或背书的名称。

- 安装包版本、WorkBuddy 版本、操作系统、测试时间和脱敏的测试员工标识；
- Token 表单成功、普通 Skill 检索/读取工具和 7 个探索工具可发现，企业 Skill 助手及需求探索快捷入口均可识别；
- 企业 Skill 助手能按名称、简介、分类和标签检索员工可见的普通 Skill，从独立应用目录发现需求探索；应用 Skill 不出现在普通检索、动态 Prompt 或通用详情接口中；
- 进入需求探索后先调用状态/开始工具，受管规则正文和资源只按本人 `explorationId` 对应的锁定版本读取，不会直接采用“最新已发布但未激活”的版本；
- 入口服从锁定应用 Skill 的动态决策树，每轮询问完整当前 frontier，不以固定 1—2 个问题截断；
- 草稿保存后管理员立即可见，另一员工读取返回无权限；
- 正式提交、管理员要求补充、员工查询反馈、补充后重新提交均成功；
- 重复请求不产生重复结果，旧 revision 冲突明确，吊销/到期/停用立即拒绝；
- 所有员工侧提示均留在 WorkBuddy，不出现个人网页登录或免登录详情链接。

本地回归命令 `pnpm smoke:workbuddy` 需要可用 PostgreSQL，只证明服务端闭环，不替代真实客户端和平台审核。

在隔离测试环境完成服务端性能验收。通过密钥管理工具注入 20 枚不同测试员工令牌，不要把令牌写入命令历史、文档或报告：

```bash
WORKBUDDY_LOAD_MCP_URL=https://<测试域名>/mcp \
WORKBUDDY_LOAD_PATS=<由密钥管理工具注入的测试令牌列表> \
WORKBUDDY_LOAD_ENVIRONMENT=<环境与数据量标识> \
WORKBUDDY_LOAD_CONCURRENCY=20 \
WORKBUDDY_LOAD_ITERATIONS=10 \
WORKBUDDY_LOAD_MODE=read \
pnpm load:workbuddy
```

读链路通过后以 `WORKBUDDY_LOAD_MODE=write` 复测写链路。写模式会为每枚测试令牌创建带“性能测试”标题的草稿，只能在获批测试环境执行，并按保留期清理流程处置。保存两次 JSON 报告，确认失败数为 0、P95 不超过 3 秒，且报告包含环境、并发数、独立令牌数、请求数和持续时长。单枚令牌复用会受到员工级限流影响，工具默认拒绝把它伪装成 20 名员工的结果。

## 6. 日常运营与审计

- 管理员可查看所有成功保存的草稿和正式提交，但不能代员工编辑、提交或放弃。
- 评审只绑定正式提交快照；员工重新提交后旧评审写入必须因版本冲突被拒绝，历史评审继续保留。
- 审计页核查管理员登录、员工维护、令牌签发/吊销、规则切换、内容查看和评审。审计不得包含令牌明文、交付渠道或需求正文。
- 统计中的探索启动、保存、正式提交和完成率以服务器持久化记录为准，不以模型回复或令牌签发数量代替。
- 数据看板按近 14 天汇总需求探索错误码、次数和最近发生时间；需要定位时再到审计页筛选 `exploration.error`。错误事件只保留员工身份、状态码、请求方法、脱敏路由和是否可重试，不保存错误正文、令牌或需求内容。

## 7. 保留与删除申请清理

清理命令默认只预览。先保存 dry-run 结果并获得公司数据责任人的批准：

```bash
pnpm cleanup:explorations
```

核对待清理数量、保留期和备份策略后，才执行：

```bash
pnpm cleanup:explorations -- --execute --approved-by <审批人标识>
```

执行会清理到期业务正文及幂等响应，并保留不含正文的清理审计。数据库备份仍按公司批准的独立到期策略淘汰，不能承诺实时从全部备份删除。

员工通过公司渠道提出删除申请后，先在 dry-run 中用探索 UUID 精确核对范围，并提供不含需求正文的申请单号：

```bash
pnpm cleanup:explorations -- --exploration-id <探索 UUID> --request-ref <删除申请或工单编号>
```

经数据责任人批准后再执行同一目标；命令会原子清理该探索的修订、规则快照、正式提交、评审和幂等响应，原有审计外键置空，另留一条包含申请单号、审批人、删除数量和探索 UUID SHA-256 指纹且不含正文的删除执行记录：

```bash
pnpm cleanup:explorations -- --exploration-id <探索 UUID> --request-ref <删除申请或工单编号> --execute --approved-by <审批人标识>
```

指定探索不存在、UUID 不合法、缺少申请单号或审批人时命令会拒绝执行。不要把员工描述或需求正文放入 `--request-ref`、`--approved-by` 或命令历史。

## 8. 故障回退

| 故障 | 立即措施 | 恢复条件 |
| --- | --- | --- |
| 规则内容错误 | 切回上一已验证规则版本；隔离危险版本，影响范围不明时停用全部写入 | 新探索使用正确版本，危险版本不能继续写入且历史仍可查询 |
| 重复、错绑或越权 | 立即停用探索写入并隔离 MCP 入口，不删除证据 | 根因修复、数据核对、隔离用例和 smoke 全部通过 |
| 员工令牌泄漏 | 吊销具体令牌；范围不明时停用员工 | 新令牌定向交付且旧令牌持续被拒绝 |
| MCP 或 Registry 不可用 | 保留数据库，员工停止重试并保留 WorkBuddy 内总结 | 健康检查通过，原幂等键可安全重试或查询 |
| 连接器包错误 | 停止分发并在平台撤下/替换错误版本 | 修复包完成真实客户端回归和重新审核 |
| 数据库迁移失败 | 停止应用流量，保留日志和备份，不手工跳过失败迁移 | 在副本演练恢复或前向修复后再放流量 |

回退时不恢复员工 Web 登录、不改用共享令牌、不覆盖正式快照，也不通过回滚数据库结构删除已有成果。恢复后重新执行质量校验、PostgreSQL smoke、两个员工隔离测试和真实 WorkBuddy 关键路径。
